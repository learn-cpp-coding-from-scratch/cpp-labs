**Где в VS Code Git.** Панель **Source Control** (значок с ветвями на левой боковой панели или `Ctrl+Shift+G`, в macOS `Cmd+Shift+G`) — изменённые файлы, коммиты, отправка. Имя текущей ветки — в строке состояния внизу слева; щелчок по нему открывает список веток. Команды Git есть и в палитре команд: `Ctrl+Shift+P` (`Cmd+Shift+P`) → наберите `Git:`.

## 1. Получить новую лабораторную

Делайте это, когда преподаватель выложил новую лабораторную.

**VS Code:**
1. Перейдите в ветку `main`: щёлкните по имени ветки в строке состояния → выберите `main`.
2. Получите изменения из своего репозитория на GitHub (например, слитые ранее лабораторные): на панели **Source Control** нажмите **Sync Changes** (или значок со стрелками в строке состояния).
3. `Ctrl+Shift+P` → **Git: Pull from…** → выберите удалённый репозиторий `upstream` → ветку `upstream/main`. Новые папки лабораторных появятся в проводнике.
4. Отправьте обновления в свой репозиторий: снова **Sync Changes**.

**Командная строка:**
```sh
git switch main
git pull                           # изменения из своего репозитория на GitHub
git pull --no-edit upstream main   # новые лабораторные из репозитория преподавателя; --no-edit — стандартное сообщение слияния
git push                           # отправить их в свой репозиторий
```

Новые лабораторные приходят новыми папками и не затрагивают уже сделанную работу. Изменяйте только файлы решения в папке `src/` задачи (состав файлов описан в её `README.md`), свои тесты в `tests/student/` и свои модули библиотеки в подпапках `common/…/student/` (см. [common/README.md](common/README.md)); объявления функций не меняйте. Остальные файлы преподавателя (`CMakeLists.txt`, `CMakePresets.json`, `cmake/`, `MODULE.bazel`, `.bazelrc`, `.bazelversion`, `.clang-format`, `.clang-tidy`, `.vscode/`, `.devcontainer/`, `README.md`) не трогайте: если преподаватель тоже изменит такой файл, при получении обновлений возникнет конфликт, а проверка решения всё равно выполняется с исходными файлами.

## 2. Если преподаватель обновил курс, пока вы работаете в ветке lab-NN

Получение новой лабораторной (раздел 1) меняет только ветку `main`; ветка лабораторной, которую вы уже начали, остаётся как была. Обычно это не мешает: запрос на слияние показывает только ваши изменения, а проверка решения выполняется с актуальными файлами преподавателя. Переносить обновления в ветку лабораторной нужно, **когда об этом попросит преподаватель** — например, если он исправил тест или `CMakeLists.txt` лабораторной, которую вы сейчас делаете.

Сначала закоммитьте свою работу в ветке `lab-NN` и получите обновления в `main` (раздел 1, включая отправку `main` в свой репозиторий). Затем:

**VS Code:**
1. Перейдите в ветку лабораторной: щёлкните по имени ветки в строке состояния → выберите `lab-01`.
2. `Ctrl+Shift+P` (в macOS `Cmd+Shift+P`) → наберите `Git: Merge` → выберите команду слияния ветки → ветку `main`.
3. Отправьте ветку на GitHub: **Sync Changes**.

**Командная строка:**
```sh
git switch lab-01
git merge --no-edit main   # перенести в ветку лабораторной обновления из main
git push
```

**Что делает `git merge --no-edit main`.** `git merge` берёт коммиты ветки `main`, которых ещё нет в **текущей** ветке (после `git switch lab-01` это `lab-01`), и добавляет их в неё. Сама ветка `main` при этом не меняется.

До слияния:
```text
main:    A───B───C───U1───U2        ← U1, U2 — обновления преподавателя
                  \
lab-01:            S1───S2          ← S1, S2 — ваши коммиты с решениями
```

После `git merge main` в ветке `lab-01`:
```text
main:    A───B───C───U1───U2
                  \          \
lab-01:            S1───S2───M      ← M — коммит слияния
```

Git создаёт коммит слияния `M`, у которого два родителя — `S2` и `U2`: в ветке `lab-01` теперь есть и ваши решения, и обновления преподавателя. Если в `lab-01` ещё не было ваших коммитов, Git просто передвинет ветку вперёд до `U2`, отдельного коммита слияния не будет.

Коммиту слияния нужно сообщение. Без `--no-edit` Git откроет текстовый редактор с готовым текстом `Merge branch 'main' into lab-01` и будет ждать, пока его сохранят и закроют (в редакторе vim — набрать `:wq` и Enter). С `--no-edit` Git сразу берёт это стандартное сообщение.

Если вы и преподаватель изменили одни и те же строки одного файла, Git остановится с сообщением `CONFLICT` — что делать, см. [раздел 6](#6-если-что-то-не-работает). Если менять только файлы решений, конфликтов не бывает.

Запрос на слияние обновится сам. В нём видна разница между `lab-01` и `main` вашего репозитория на GitHub: коммиты `U1` и `U2` есть в обеих ветках, поэтому в запросе их нет, остаются только ваши `S1` и `S2`. Поэтому важен порядок: сначала `main` отправлена в свой репозиторий, потом обновления влиты в ветку лабораторной. Если получить обновления, находясь в ветке `lab-NN`, или не отправить `main`, в запросе на слияние окажутся чужие файлы — изменения преподавателя.

## 3. Выполнить лабораторную

Каждая лабораторная выполняется в своей ветке `lab-NN`, где `NN` — номер лабораторной.

**VS Code:**
1. **Создать ветку.**
   - Проверьте, что вы в ветке `main`: в левом нижнем углу окна, в строке состояния, рядом со значком ветвления написано имя текущей ветки — должно быть `main`. Проверьте, что новая лабораторная получена (раздел 1): на панели **Explorer** (`Ctrl+Shift+E`, в macOS `Cmd+Shift+E`) есть её папка, например `lab-01_linear-algorithms`.
   - Щёлкните по имени ветки `main` в строке состояния. Вверху по центру окна откроется список: пункты **+ Create new branch…**, **+ Create new branch from…** и ниже — существующие ветки.
   - Выберите **+ Create new branch…**, введите `lab-01` и нажмите Enter.
   - В строке состояния вместо `main` появится `lab-01`: ветка создана от ветки `main`, в которой вы были, и VS Code уже переключился на неё.

   Если имени ветки в строке состояния не видно, создайте ветку через палитру команд: `Ctrl+Shift+P` (в macOS `Cmd+Shift+P`) → **Git: Create Branch…** → `lab-01` → Enter.
2. **Решайте задачи** (как устроена задача — в [README.md](README.md)).
3. **Сохраняйте работу коммитом** после каждой решённой задачи:
   - откройте панель **Source Control** — там список изменённых файлов; щелчок по файлу показывает, что в нём изменилось;
   - нажмите **+** у файлов, которые входят в коммит (или **+** у заголовка **Changes** — все сразу);
   - введите сообщение в поле **Message**, например `feat(lab-01): реализовать задачу 3 — обмен значений`, и нажмите **Commit**. Сообщения желательно оформлять по соглашению **Conventional Commits**: тип изменения (`feat`, `fix` …), в скобках — лабораторная, после двоеточия — что сделано; подробно — в [GIT.md](GIT.md#оформление-по-conventional-commits-желательно).
4. **Отправьте ветку на GitHub:** первый раз — кнопка **Publish Branch**, дальше — **Sync Changes**.

**Командная строка:**
```sh
git switch main
git switch -c lab-01                  # создать ветку и перейти в неё
git add lab-01_linear-algorithms
git commit -m "feat(lab-01): реализовать задачу 3 — обмен значений"
git push -u origin lab-01             # первая отправка ветки; дальше достаточно git push
```

Как часто коммитить, как писать сообщения коммитов (в том числе по Conventional Commits — [GIT.md](GIT.md#оформление-по-conventional-commits-желательно)) и другие полезные команды Git — в шпаргалке [GIT.md](GIT.md).

### По желанию: решение в виде модуля C++20

В задачах, где рядом с `.hpp` и `.cpp` лежит файл `src/<имя>.cppm.example`, решение можно оформить модулем C++20: переименуйте файл в `<имя>.cppm`, а `include/<имя>.hpp` и `src/<имя>.cpp` удалите. CMake сам соберёт задачу из модуля, а тесты подключат его объявлением `import`. Модули собираются не всеми компиляторами:

- **macOS:** Apple Clang модули через CMake не собирает — установите LLVM (`brew install llvm`) и выберите пресет **llvm-debug**;
- **контейнер:** обычный пресет **debug** — Clang там компилятор по умолчанию;
- **Linux и WSL (на Windows):** установите Clang той же версии, что clang-tidy, вместе с `clang-tools` (в нём `clang-scan-deps`) — в Debian и Ubuntu `sudo apt install clang clang-tools` — и выберите пресет **clang-debug**;
- **Windows** (g++ из MSYS2 или MSVC) и **g++ в Linux и WSL (на Windows):** модули собираются, но clang-tidy их не проверяет — CMake отключит его для такой задачи и выведет предупреждение. Чтобы модули проверялись clang-tidy, работайте в контейнере ([SETUP.md](SETUP.md), раздел 1).

Если модуль у вас не собирается, оставьте решение в `.hpp` и `.cpp`: модули не обязательны.

### По желанию: сборка Bazel вместо CMake

Проект можно собирать системой сборки Bazel. Установите Bazelisk — он запускает Bazel той версии, что указана в файле `.bazelversion`: Windows — `winget install Bazel.Bazelisk`, macOS — `brew install bazelisk`, Linux — файл `bazelisk-linux-amd64` со страницы [выпусков Bazelisk](https://github.com/bazelbuild/bazelisk/releases), переименованный в `bazel`; в контейнере Bazelisk уже установлен.

Зависимости и флаги уже описаны в `MODULE.bazel` и `.bazelrc`, библиотека `common` — в `common/BUILD.bazel`. Файл `BUILD.bazel` задачи напишите сами и положите в папку задачи, рядом с её `CMakeLists.txt` и `README.md` (например, `lab-04_arrays/task-01_missing-digit/BUILD.bazel`): пути к файлам в нём указываются от этой папки. Образец:

```python
load("@rules_cc//cc:defs.bzl", "cc_binary", "cc_library", "cc_test")

cc_library(
    name = "lib",
    srcs = ["src/missing_digit.cpp"],
    hdrs = ["include/missing_digit.hpp"],
    includes = ["include"],
    deps = ["//common:cpplabs"],
)

cc_binary(
    name = "missing-digit",
    srcs = ["src/missing_digit_main.cpp"],
    deps = [":lib"],
)

cc_test(
    name = "tests",
    size = "small",
    srcs = ["tests/open/missing_digit_test.cpp"],
    deps = [
        ":lib",
        "@googletest//:gtest_main",
    ],
)
```

```sh
bazel test //lab-04_arrays/task-01_missing-digit:all          # тесты задачи
bazel run  //lab-04_arrays/task-01_missing-digit:missing-digit # программа
```

Bazel не запускает clang-tidy: стиль проверяйте в VS Code, сборкой CMake или командой `clang-tidy` в терминале (см. «Проверка стиля clang-tidy» в разделе «Сборка и запуск в терминале» [README.md](README.md)). Модули C++20 собирайте только через CMake. Сдаются те же файлы задачи, что и при сборке CMake, — преподаватель проверяет решение через CMake.

## 4. Сдать лабораторную

Запрос на слияние создаётся, рецензируется и сливается **в браузере, на сайте GitHub** — при любом способе работы с Git (пункты 2, 3 и 5).

**VS Code и GitHub:**
1. Отправьте последние коммиты: **Sync Changes**.
2. Откройте в **браузере** страницу своего репозитория на сайте GitHub: `https://github.com/<ваш-логин>/cpp-labs` (войдите в аккаунт, если сайт попросит). Вверху страницы откройте вкладку **Pull requests** → кнопка **New pull request** → в списках выберите **base: `main`** и **compare: `lab-01`** → **Create pull request**. В описании перечислите решённые задачи. Если ветка отправлена недавно, на главной странице репозитория GitHub сам показывает строку «lab-01 had recent pushes…» с кнопкой **Compare & pull request** — она открывает ту же форму.
3. В той же форме в браузере, в правой колонке, в поле **Reviewers** выберите преподавателя лабораторных (если забыли, рецензента можно выбрать и позже — на странице уже созданного запроса на слияние, в той же правой колонке).
4. Преподаватель запускает на вашем решении свои тесты и оставляет замечания к строкам кода. Исправляйте их **в той же ветке**: проверьте в строке состояния, что вы в `lab-01`, внесите исправления, сделайте коммит (например, `fix(lab-01): исправить обработку отрицательных чисел в задаче 3`) и нажмите **Sync Changes** — исправления сразу появятся в том же запросе на слияние.
5. Когда преподаватель одобрит работу (**Approve**), на странице запроса на слияние в браузере нажмите **Merge pull request** → **Confirm merge**. Затем в VS Code перейдите в ветку `main` и нажмите **Sync Changes** — слитая работа появится и у вас.

**Командная строка** — отправка (пункт 1), исправления (пункт 4) и обновление `main` после слияния (пункт 5):
```sh
git push                              # пункт 1
git switch lab-01                     # пункт 4
git commit -am "fix(lab-01): исправить обработку отрицательных чисел в задаче 3"   # -a: все изменённые отслеживаемые файлы; новый файл сначала git add
git push
# после Merge pull request на GitHub:
git switch main
git pull
```

Срок сдачи каждой лабораторной указан в её `README.md`. Лабораторная считается сданной, когда запрос на слияние одобрен.

### После слияния: удалите ветку лабораторной

После **Merge pull request** ветка `lab-01` сама не удаляется: она остаётся и на GitHub, и на вашем компьютере. Удалите её в обоих местах:

1. **На GitHub (в браузере).** Сразу после слияния на странице запроса на слияние появляется кнопка **Delete branch** — нажмите её.
2. **На компьютере.** Перейдите в ветку `main` (её нужно обновить — **Sync Changes**, см. пункт 5) и удалите `lab-01`:
   - **VS Code:** `Ctrl+Shift+P` (в macOS `Cmd+Shift+P`) → **Git: Delete Branch…** → выберите `lab-01`;
   - **командная строка:** `git branch -d lab-01`.
3. **Уберите запись об удалённой ветке GitHub** (`origin/lab-01`, она остаётся у вас после шага 1): **VS Code** — `Ctrl+Shift+P` → **Git: Fetch (Prune)**; **командная строка** — `git fetch --prune`.

Удалять текущую ветку Git не разрешает, поэтому сначала перейдите в `main`. Если ветка ещё не слита в `main`, команда `git branch -d` откажется её удалять (`not fully merged`), а VS Code предложит удалить принудительно — **откажитесь**: значит, `main` у вас не обновлена (выполните **Sync Changes** в `main`) или запрос на слияние ещё не слит. Так случайно потерять работу нельзя.

**Удаление ветки ничего не уничтожает.** Все коммиты `lab-01` после слияния входят в историю `main`. Запрос на слияние — со всеми коммитами, замечаниями преподавателя и одобрением — остаётся на GitHub во вкладке **Pull requests → Closed**, и для этого ветка не нужна.

**Можно и не удалять.** Если хотите видеть, какие ветки были, оставьте их: работе это не мешает, просто к концу семестра в списке будут `lab-01` … `lab-10`. Чтобы GitHub удалял ветки сам после каждого слияния, включите в своём репозитории **Settings → General → Automatically delete head branches**.

**Не продолжайте работу в ветке, которая уже слита.** Запрос на слияние после **Merge** закрыт, и новые коммиты в `lab-01` в него не попадут: ни в `main`, ни к преподавателю они сами не придут — для этого понадобится новый запрос на слияние. Кроме того, старая ветка создана от прежнего состояния `main`: в ней нет новых лабораторных и того, что слито позже, поэтому при новом слиянии вероятны конфликты. Если после слияния понадобилось что-то исправить, создайте **новую ветку от актуальной `main`**, например `lab-01-fix` (раздел 3), и сдайте исправление новым запросом на слияние. Удалённая после слияния ветка не даст по ошибке продолжить работу в старой.

## 5. Если вам удобнее GitHub Desktop

[GitHub Desktop](https://desktop.github.com) — отдельная программа для работы с Git мышкой: видны изменённые файлы, история и ветки. Основные способы в курсе — VS Code и командная строка (разделы 1–4); GitHub Desktop — для тех, кому он привычнее. Она есть для Windows и macOS (официальной версии для Linux нет). Установка: в Windows — `winget install GitHub.GitHubDesktop`, в macOS — `brew install --cask github`.

Первичная настройка ([SETUP.md](SETUP.md), разделы 4 и 5) всё равно выполняется **в терминале**: GitHub Desktop не умеет подключать репозиторий преподавателя как `upstream`. После неё:

1. **Вход в GitHub.** При первом запуске нажмите **Sign in to GitHub.com** и войдите через браузер; на шаге **Configure Git** проверьте имя и почту.
2. **Подключить свою копию.** **File → Add Local Repository** → выберите папку `cpp-labs`.
3. **Получить новую лабораторную.**
   - В списке **Current Branch** выберите `main`.
   - Загрузите изменения преподавателя: **Repository → Open in Terminal** (в Windows пункт называется по оболочке, выбранной в настройках, например **Open in Command Prompt**) и выполните `git fetch upstream`.
   - **Branch → Merge into current branch** → выберите `upstream/main` → **Merge**.
   - Нажмите **Push origin**, чтобы отправить обновления в свой репозиторий.
   - Если преподаватель попросил перенести обновления в начатую ветку лабораторной: выберите в **Current Branch** ветку `lab-01` → **Branch → Merge into current branch** → `main` → **Merge** → **Push origin**.
4. **Начать лабораторную.** **Branch → New branch** → имя `lab-01`, основа — `main` → **Create branch**.
5. **Сохранить работу.** Отметьте изменённые файлы слева, внизу введите сообщение (например, `feat(lab-01): реализовать задачу 3 — обмен значений`) → **Commit to lab-01**. Затем **Publish branch** (первый раз) или **Push origin**.
6. **Сдать.** **Branch → Create Pull Request** — откроется браузер; проверьте **base: `main`** и **compare: `lab-01`**, выберите преподавателя в **Reviewers** → **Create pull request**. Исправления по замечаниям — новые коммиты в той же ветке и **Push origin**.
7. **После одобрения** нажмите на GitHub **Merge pull request**, затем в GitHub Desktop выберите ветку `main` и нажмите **Fetch origin** → **Pull origin**.

GitHub Desktop и VS Code работают с одной и той же папкой: можно писать код в VS Code, а коммитить и отправлять в GitHub Desktop.

## 6. Если что-то не работает

| Сообщение или симптом | Что сделать |
|---|---|
| `CMake was unable to find a build program corresponding to "Ninja"` | Ninja не установлен или его папки нет в `PATH` (в Windows — `C:\msys64\ucrt64\bin`, см. [SETUP.md](SETUP.md), раздел 1) |
| `No CMAKE_CXX_COMPILER could be found` | компилятор не установлен или его папки нет в `PATH`; перезапустите VS Code после изменения `PATH` |
| `clang-tidy не найден — сборка без проверки стиля` | установите clang-tidy (в macOS — команда `ln -s …` из [SETUP.md](SETUP.md), раздел 1) |
| macOS: `'cctype' file not found` при проверке clang-tidy | не выполнена команда `echo 'export SDKROOT=…'` из [SETUP.md](SETUP.md), раздел 1; выполните её и перезапустите терминал и VS Code |
| macOS: `zsh: command not found: code` | VS Code скачан с сайта: в VS Code `Cmd+Shift+P` → **Shell Command: Install 'code' command in PATH**, затем новое окно терминала |
| VS Code не предлагает пресеты, нет панели CMake | открыта не корневая папка репозитория или не установлено расширение CMake Tools |
| Ошибки `#include` в редакторе, хотя проект собирается | `Ctrl+Shift+P` → **CMake: Delete Cache and Reconfigure** |
| VS Code: `Docker is not running` или `Cannot connect to the Docker daemon` при **Reopen in Container** | запустите Docker Desktop и повторите; в Linux после `usermod -aG docker` нужно выйти из системы и войти снова |
| **Reopen in Container** или Codespaces: `denied`, `unauthorized` или `403` при скачивании образа `ghcr.io/learn-cpp-coding-from-scratch/cpp-labs-dev` | образ курса недоступен для скачивания — это не ваша ошибка: напишите преподавателю и пока работайте без контейнера ([SETUP.md](SETUP.md), раздел 1) |
| `The current CMakeCache.txt directory … is different` или `Does not match the generator used previously` | проект собирался в другом окружении (в контейнере или без него, на другом компьютере): удалите папку `build/` и повторите настройку |
| WSL: сборка очень медленная, VS Code не замечает изменений файлов | репозиторий лежит на диске Windows (путь начинается с `/mnt/c/`): склонируйте его заново в домашнюю папку Linux (`cd ~`, [SETUP.md](SETUP.md), «Другой вариант для Windows: Linux в WSL») |
| При первой настройке проекта — ошибка загрузки googletest или spdlog | CMake скачивает библиотеки из интернета; проверьте подключение и повторите |
| `git push` → `Authentication failed`, `Permission … denied` или запрос пароля | войдите в GitHub одним из способов [SETUP.md](SETUP.md), раздел 4, в отдельном терминале — командой `gh auth login`; проверьте командой `git remote -v`, что `origin` указывает на **ваш** репозиторий, а не на репозиторий преподавателя |
| `git pull` → `Need to specify how to reconcile divergent branches` | выполните `git config --global pull.rebase false` ([SETUP.md](SETUP.md), раздел 4) и повторите |
| `git push` → `rejected … fetch first` | в репозитории на GitHub есть изменения, которых нет у вас: `git pull`, затем снова `git push` |
| `git pull upstream main` → `CONFLICT` | вы изменили файл преподавателя. Отмените слияние `git merge --abort`, верните файл командой `git checkout upstream/main -- <файл>`, сделайте коммит и повторите `git pull --no-edit upstream main`; если не получается — напишите преподавателю |
| `git merge main` в ветке `lab-NN` → `CONFLICT` | вы изменили файл преподавателя. Отмените слияние `git merge --abort`, верните файл командой `git checkout main -- <файл>`, сделайте коммит и повторите `git merge --no-edit main`; если не получается — напишите преподавателю |
| В запросе на слияние видны файлы, которые вы не меняли | обновления преподавателя попали в ветку `lab-NN`, а `main` в вашем репозитории на GitHub осталась старой: перейдите в `main` и выполните `git pull --no-edit upstream main` и `git push` (раздел 1) — запрос обновится сам |
| Сделали коммит не в той ветке (например, в `main`) | ничего не удаляйте и напишите преподавателю — см. раздел «Отменить» в [GIT.md](GIT.md#отменить) |

Как вернуть испорченный файл, убрать лишний файл из коммита, исправить сообщение последнего коммита или отменить уже отправленный коммит — в разделе «Отменить» шпаргалки [GIT.md](GIT.md#отменить). Там же — какие команды выполнять нельзя.
