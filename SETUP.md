## 1. Установка инструментов

Для лабораторных нужны:

| Программа | Зачем |
|---|---|
| компилятор C++ (g++ или clang++) и отладчик (gdb или lldb) | компиляция и отладка программ |
| CMake и Ninja | сборка проекта |
| clang-tidy и clang-format | проверка и форматирование кода по стилю курса |
| Git и GitHub CLI (`gh`) | работа с репозиторием и вход в GitHub |
| VS Code | среда разработки |

Устанавливайте программы менеджером пакетов, как ниже: так нужные версии ставятся и обновляются командами, без поиска установщиков на разных сайтах.

**Как связаны CMake и Ninja.** Сборка идёт в два этапа. **CMake** читает описание проекта (`CMakeLists.txt`: какие программы, из каких файлов, с какими флагами), находит компилятор и инструменты, находит или скачивает библиотеки Google Test и Catch2 (тестирование) и spdlog (логирование) и пишет подробный план сборки — файл `build.ninja` в папке сборки (для пресета `debug` — `build/debug/build.ninja`). Сам CMake ничего не компилирует. **Ninja** выполняет этот план: запускает компилятор, clang-tidy и компоновщик в нужном порядке, по несколько команд одновременно (по умолчанию — по числу ядер процессора с небольшим запасом) и повторяет только те шаги, результат которых зависит от файлов, изменившихся с прошлой сборки (если не изменилось ничего, он пишет `ninja: no work to do.`). Вручную запускать Ninja не нужно — это делают CMake и VS Code (кнопка **Build**), но установлен он должен быть: настройки проекта (`CMakePresets.json`) указывают именно его.

### Windows

**Что такое MSYS2, MinGW-w64 и UCRT64.** В Windows курс использует компилятор **g++** из коллекции компиляторов **GCC** проекта GNU — тот же, что в Linux, — и отладчик **gdb** того же проекта. Чтобы GCC создавал программы для Windows, ему нужны заголовочные файлы и библиотеки для вызова функций Windows (Windows API) и стандартной библиотеки языка C из состава Windows. Их предоставляет проект **MinGW-w64** (Minimalist GNU for Windows); GCC вместе с ними создаёт обычные программы Windows (`.exe`). GCC и gdb, собранные для Windows с MinGW-w64, называют набором инструментов (toolchain) MinGW-w64. Готовые сборки GCC, gdb и остальных инструментов курса для Windows устанавливаются через **MSYS2** — набор программ для Windows с терминалом bash и менеджером пакетов `pacman`, который устанавливает и обновляет пакеты одной командой (как `apt` в Linux или `brew` в macOS). В MSYS2 есть несколько **окружений** — независимых наборов пакетов, у каждого свой терминал и своя папка. Курс использует окружение **UCRT64**: его программы используют **UCRT** (Universal C Runtime) — библиотеку среды выполнения языка C, встроенную в Windows 10 и 11; это окружение MSYS2 рекомендует по умолчанию. Поэтому пакеты устанавливаются в терминале **MSYS2 UCRT64**, их имена начинаются с `mingw-w64-ucrt-x86_64-`, а программы оказываются в папке `C:\msys64\ucrt64\bin` (если MSYS2 установлена в папку по умолчанию).

1. Установите среду **MSYS2** со страницы https://www.msys2.org (установщик, путь по умолчанию `C:\msys64`).
2. Откройте из меню «Пуск» терминал **MSYS2 UCRT64** и выполните (на вопросы отвечайте Enter, после первой команды терминал может закрыться — откройте его снова и повторите её):
   ```sh
   pacman -Syu
   pacman -S mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-gdb \
             mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja \
             mingw-w64-ucrt-x86_64-clang mingw-w64-ucrt-x86_64-clang-tools-extra
   ```

   | Пакет `mingw-w64-ucrt-x86_64-…` | Что внутри |
   |---|---|
   | `gcc` | компиляторы GCC: `gcc` (язык C) и `g++` (язык C++) |
   | `gdb` | отладчик gdb — им VS Code отлаживает программы по F5 |
   | `cmake`, `ninja` | CMake и Ninja — сборка проекта |
   | `clang`, `clang-tools-extra` | инструменты проекта LLVM: clang-format (форматирование кода) и clang-tidy (проверка стиля и типичных ошибок при каждой сборке); компилятор Clang из этих пакетов курс не использует |
3. Добавьте папку `C:\msys64\ucrt64\bin` в переменную среды `Path`: **Параметры → Система → О системе → Дополнительные параметры системы → Переменные среды**, в разделе «Переменные среды пользователя» выберите `Path` → **Изменить** → **Создать**. Команды вроде `g++`, `cmake`, `ninja` Windows ищет в папках из `Path`, поэтому без этого VS Code и обычный терминал Windows их не найдут. Добавлять нужно именно `ucrt64\bin`. Папки `mingw64\bin`, `clang64\bin` и `usr\bin` принадлежат другим окружениям MSYS2: их программы собраны для других библиотек среды выполнения, и если такая папка окажется в `Path` раньше `ucrt64\bin`, будут запускаться не те программы.
4. В **PowerShell** установите Git, GitHub CLI и VS Code:
   ```powershell
   winget install Git.Git GitHub.cli Microsoft.VisualStudioCode
   ```
5. Перезагрузите компьютер (или хотя бы закройте все терминалы), чтобы изменения `Path` вступили в силу.

**Другой вариант компилятора для Windows — MSVC.** Вместо MSYS2 (пункты 1–3) можно взять компилятор Microsoft **MSVC**. Он устанавливается вместе со средой разработки **Visual Studio** (это отдельная программа, не VS Code): в установщике Visual Studio выберите компонент «Разработка классических приложений на C++» — с ним устанавливаются компилятор MSVC, CMake, Ninja и clang-format. clang-tidy устанавливается дополнительно: компонент «Инструменты C++ Clang для Windows» в том же установщике или командой `winget install LLVM.LLVM`. Visual Studio в этом варианте нужна только как источник компилятора и инструментов: лабораторные вы по-прежнему выполняете в **VS Code**, как описано ниже, и выбираете в нём пресет **Debug (MSVC)** вместо **Debug (GCC/Clang)**. Git, GitHub CLI и VS Code установите командой из пункта 4.

**Работать в самой Visual Studio**, а не в VS Code, тоже можно: установка, сборка, тесты, отладка и Git в Visual Studio описаны в отдельной заметке [VISUAL_STUDIO.md](VISUAL_STUDIO.md).

Ещё два варианта для Windows — Linux в WSL и контейнер — описаны ниже, после Linux.

### macOS

Откройте приложение **Терминал** и выполните по очереди. Команда `xcode-select --install` открывает отдельное окно установки: нажмите **Install** и дождитесь окончания (несколько минут), только потом выполняйте следующие команды. Сообщение `command line tools are already installed` не ошибка: инструменты уже есть, переходите дальше.
```sh
setopt interactivecomments
echo 'setopt interactivecomments' >> ~/.zshrc
xcode-select --install          # компилятор clang++, отладчик lldb, git

# менеджер пакетов Homebrew (команда со страницы https://brew.sh); в конце установщик
# выведет в разделе Next steps команды для добавления Homebrew в PATH — выполните их
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

brew install cmake ninja clang-format llvm gh
brew install --cask visual-studio-code

# clang-tidy входит в пакет llvm, но Homebrew не делает его доступной командой — создаём ссылку
ln -s "$(brew --prefix llvm)/bin/clang-tidy" "$(brew --prefix)/bin/clang-tidy"
# clang-tidy из Homebrew не знает, где лежат стандартные заголовки macOS — подсказываем ему
echo 'export SDKROOT="$(xcrun --show-sdk-path)"' >> ~/.zprofile
```
После этого закройте и снова откройте терминал и VS Code.

Если VS Code установлен не через Homebrew, а скачан с сайта https://code.visualstudio.com, команда `code` в терминале сама не появляется. Подключите её: откройте VS Code → `Cmd+Shift+P` → **Shell Command: Install 'code' command in PATH** → Enter, затем откройте новое окно терминала. Команда `code` нужна для установки расширений из терминала (раздел 3) и для настройки Git (раздел 4).

Первые две строки нужны из-за оболочки zsh, которая по умолчанию работает в терминале macOS: в ней текст после `#` в командах, набранных или вставленных в терминал, по умолчанию **не** считается комментарием, а передаётся команде как аргументы — и команда вида `git push   # пояснение` завершится ошибкой. Команда `setopt interactivecomments` включает комментарии в текущем окне терминала, а строка в файле `~/.zshrc` — во всех следующих. В этой инструкции пояснения после `#` стоят во многих командах, поэтому выполните эти строки первыми. В Windows (PowerShell) и Linux (bash) комментарии работают без настройки.

### Linux (Debian, Ubuntu)

```sh
sudo apt update
sudo apt install build-essential gdb cmake ninja-build git gh clang-format clang-tidy
sudo snap install code --classic        # VS Code
```
Проекту нужен CMake 3.24 или новее (проверка — в разделе 2). В Ubuntu 24.04 и Debian 12 `apt` ставит подходящую версию, а в Ubuntu 22.04 — 3.22; в этом случае установите CMake из snap: `sudo snap install cmake --classic`.

Если `snap` нет, скачайте пакет VS Code `.deb` со страницы https://code.visualstudio.com и установите его: `sudo apt install ./code_*.deb`. В других дистрибутивах те же программы устанавливаются их менеджером пакетов (в Fedora — `sudo dnf install gcc-c++ gdb cmake ninja-build git gh clang-tools-extra`).

### Другой вариант для Windows: Linux в WSL

**WSL** (Windows Subsystem for Linux, подсистема Windows для Linux) запускает настоящий Linux — обычно Ubuntu — прямо в Windows, без отдельной виртуальной машины, которую нужно настраивать. Вместо MSYS2 (раздел «Windows», пункты 1–3) можно установить инструменты курса в Ubuntu в WSL — теми же командами, что в Linux. VS Code при этом остаётся программой Windows, а компилирует, запускает и отлаживает программы в Linux через расширение **WSL**. Нужна Windows 10 версии 2004 или новее либо Windows 11.

1. Откройте **PowerShell от имени администратора** (правый щелчок по «Пуск» → **Терминал (администратор)**) и выполните:
   ```powershell
   wsl --install
   ```
   Команда включит WSL и установит Ubuntu. Перезагрузите компьютер. После перезагрузки откроется окно Ubuntu (если не открылось — запустите **Ubuntu** из меню «Пуск»): придумайте имя пользователя Linux и пароль. Пароль понадобится для `sudo`; при вводе он не отображается — так и должно быть.
2. В окне **Ubuntu** установите инструменты (VS Code в Ubuntu не ставится — он устанавливается в Windows, пункт 3):
   ```sh
   sudo apt update
   sudo apt install build-essential gdb cmake ninja-build git gh clang-format clang-tidy
   ```
3. В **PowerShell** (обычном) установите VS Code и расширение WSL (`ms-vscode-remote.remote-wsl`):
   ```powershell
   winget install Microsoft.VisualStudioCode
   code --install-extension ms-vscode-remote.remote-wsl
   ```
   Если `code` не найдена — закройте и снова откройте PowerShell. Git и GitHub CLI для Windows в этом варианте не нужны: ими пользуется Linux.

**Дальше всё — в терминале Ubuntu:** проверка установки (раздел 2), настройка Git и вход в GitHub командой `gh auth login` (раздел 4), своя копия репозитория (раздел 5). Linux в WSL — отдельная система со своими настройками Git: настройки Git для Windows на него не действуют.

**Храните репозиторий в Linux**, в домашней папке (`cd ~` перед `git clone` в разделе 5), а не на диске Windows (`/mnt/c/…`): с диском Windows сборка идёт в несколько раз медленнее, а VS Code может не замечать изменений файлов. Из Проводника Windows эта папка видна как `\\wsl$\Ubuntu\home\<имя>\cpp-labs`.

**Открыть проект в VS Code:** в терминале Ubuntu выполните `cd ~/cpp-labs` и `code .`. Признак того, что VS Code работает с Linux, — надпись **WSL: Ubuntu** в левом нижнем углу окна. Расширения C/C++ и CMake Tools устанавливаются отдельно для WSL: VS Code сам предложит **Install in WSL** (раздел 3). Терминал VS Code в этом режиме — терминал bash в Ubuntu, пресет сборки — **Debug (GCC/Clang)**.

### Другой вариант: контейнер с готовыми инструментами. Docker на своём компьютере или GitHub Codespaces в браузере

Вместо установки компилятора, CMake, Ninja, clang-tidy и clang-format можно работать в **контейнере**. Контейнер — запущенная в изолированной среде группа процессов Linux со своей файловой системой; её содержимое берётся из **образа** — неизменяемого набора файлов с уже установленными программами. Контейнеры запускает программа **Docker**; в Windows и macOS она запускает их внутри виртуальной машины Linux. Для курса образ уже собран (Ubuntu 26.04): в нём компилятор Clang 23 — он выбран по умолчанию, — а также g++ 15, gdb, CMake, Ninja, Bazel, clang-tidy и clang-format той же версии, что у преподавателя, и библиотеки Google Test, Catch2 и spdlog. Как запускать контейнер, VS Code узнаёт из папки `.devcontainer/` репозитория. Папка репозитория остаётся на вашем компьютере (или в облаке, способ Б), а в контейнере она видна как `/workspaces/cpp-labs`: файлы, которые вы правите, — те же самые.

Способов два: **А** — Docker на своём компьютере, **Б** — GitHub Codespaces в браузере, на своём компьютере ничего не устанавливается.

**А. Docker на своём компьютере.** Нужно 4 ГБ оперативной памяти, а лучше 8, и около 3 ГБ на диске: образ при первом запуске скачивается (около 350 МБ) и занимает 1,4 ГБ.
1. Установите Git, GitHub CLI, VS Code и Docker; компилятор, CMake и остальное из начала раздела **не** нужны.
   - **Windows** (PowerShell):
     ```powershell
     winget install Git.Git GitHub.cli Microsoft.VisualStudioCode Docker.DockerDesktop
     ```
     Docker Desktop в Windows работает через подсистему WSL 2: если установщик попросит её включить или перезагрузить компьютер, согласитесь. Если Docker Desktop сообщает, что виртуализация отключена (`Virtualization support not detected`), её нужно включить в настройках BIOS/UEFI компьютера (пункт *Intel Virtualization Technology*, *VT-x*, *AMD-V* или *SVM*).
   - **macOS** (сначала первые две строки и установка Homebrew из блока для macOS выше):
     ```sh
     xcode-select --install          # git
     brew install gh
     brew install --cask visual-studio-code docker-desktop
     ```
   - **Linux** (Debian, Ubuntu):
     ```sh
     sudo apt install git gh docker.io
     sudo snap install code --classic
     sudo usermod -aG docker $USER   # запуск docker без sudo; действует после выхода из системы и входа
     ```
2. Запустите Docker Desktop (в Linux Docker запущен как служба). Пока он не запущен, VS Code не сможет открыть контейнер.
3. Установите в VS Code расширение **Dev Containers** (`ms-vscode-remote.remote-containers`): `code --install-extension ms-vscode-remote.remote-containers`.
4. Выполните раздел 4 (Git и GitHub) и раздел 5 (своя копия репозитория) на своём компьютере, как всем. VS Code передаёт в контейнер настройки Git (`user.name`, `user.email` и другие) и вход в GitHub, поэтому в контейнере их повторять не нужно.
5. Откройте папку `cpp-labs` в VS Code. Внизу справа появится предложение **Reopen in Container** — нажмите его (или `Ctrl+Shift+P` → **Dev Containers: Reopen in Container**). Первый запуск занимает несколько минут: скачивается образ. Признак того, что вы в контейнере, — надпись **Dev Container: cpp-labs** в левом нижнем углу окна. В контейнере установлены расширения C/C++ и CMake Tools, терминал VS Code — это терминал bash в контейнере, пресет сборки — **Debug (GCC/Clang)**.

В следующий раз VS Code откроет папку сразу в контейнере (Docker должен быть запущен). Вернуться к работе без контейнера: `Ctrl+Shift+P` → **Dev Containers: Reopen Folder Locally**. Если вы собираете проект то в контейнере, то без него, перед сменой удалите папку `build/`: CMake запоминает в ней пути и компилятор и в другом окружении остановится с ошибкой.

**Если контейнер не открывается** — например, VS Code сообщает, что Docker не запущен, или образ не скачивается из-за ошибки `denied`, — найдите сообщение в таблице раздела «Если что-то не работает» [WORKFLOW.md](WORKFLOW.md#6-если-что-то-не-работает).

**Б. GitHub Codespaces — в браузере.** Codespace — такой же контейнер, но он работает на сервере GitHub, а VS Code открывается в браузере. Подходит, если компьютер слабый или чужой (например, в аудитории).

Codespaces бесплатен в пределах **личной** месячной квоты вашего аккаунта GitHub: codespace создаётся в вашем репозитории, и время его работы учитывается у вас, а не у преподавателя или курса. Квота — 120 «ядро-часов» в месяц, то есть 60 часов работы codespace с 2 ядрами, и 15 ГБ хранилища; с [GitHub Student Developer Pack](https://education.github.com/pack) — 180 ядро-часов и 20 ГБ. Сколько израсходовано, показывает страница https://github.com/settings/billing. Если квота закончится, codespace не запустится до следующего месяца; деньги без привязанной карты не списываются. Неработающий codespace останавливается сам через 30 минут, но время учитывается, пока он запущен: закончив, остановите его (**Code → Codespaces → … → Stop codespace**). Остановленный codespace сохраняет файлы, но занимает место в квоте хранилища.

**Остановленный codespace, которым не пользовались 30 дней, GitHub удаляет автоматически** — вместе со всеми изменениями, которые не отправлены в ваш репозиторий на GitHub (неотправленные коммиты удаление не останавливают). Поэтому в конце каждого занятия отправляйте коммиты на GitHub ([WORKFLOW.md](WORKFLOW.md), раздел 3, шаг 4): в ваш репозиторий на GitHub они сохраняются навсегда, а codespace при необходимости можно создать заново.
1. Сделайте свою приватную копию репозитория без командной строки: на GitHub **+** → **Import repository**, адрес `https://github.com/learn-cpp-coding-from-scratch/cpp-labs.git`, имя `cpp-labs`, видимость **Private** → **Begin import**. Пригласите преподавателя (раздел 5, шаг 3).
2. На странице своего репозитория: **Code → Codespaces → Create codespace on main**. Первый запуск занимает несколько минут.
3. В терминале codespace (один раз для каждого codespace) подключите репозиторий преподавателя и задайте настройки Git из раздела 4 (имя и почту GitHub задаёт сам):
   ```sh
   git remote add upstream https://github.com/learn-cpp-coding-from-scratch/cpp-labs.git
   git config --global pull.rebase false
   git config --global core.editor "code --wait"
   ```
   Вход в GitHub для вашего репозитория в codespace уже выполнен.
4. Дальше — получение, выполнение и сдача лабораторных по [WORKFLOW.md](WORKFLOW.md), как обычно. Изменения хранятся в codespace, пока вы не отправили их в свой репозиторий (**Sync Changes** или `git push`): не удаляйте codespace с неотправленными коммитами.

## 2. Проверка установки

Откройте **новый** терминал (в Windows — PowerShell или терминал VS Code, в WSL — терминал Ubuntu) и выполните:
```sh
g++ --version
cmake --version
ninja --version
clang-tidy --version
clang-format --version
git --version
gh --version
code --version
```
Блок можно скопировать и вставить в терминал целиком (`Ctrl+V`, в macOS `Cmd+V`), затем нажать Enter: команды выполнятся по очереди. Каждая команда должна вывести номер версии; версия CMake должна быть 3.24 или новее. В macOS команда `g++` запускает компилятор clang++ — так и должно быть. Сообщение `command not found` (в PowerShell — «Имя … не распознано как имя командлета, функции, файла сценария или выполняемой программы», в командной строке Windows — «… не является внутренней или внешней командой») означает, что программа не установлена или её папки нет в `PATH`; после изменения `PATH` перезапустите терминал и VS Code.

## 3. VS Code: расширения и настройка

Обязательные расширения:

| Расширение | Идентификатор | Зачем |
|---|---|---|
| **C/C++** (Microsoft) | `ms-vscode.cpptools` | подсветка и подсказки (IntelliSense), отладка, проверка clang-tidy, форматирование |
| **CMake Tools** (Microsoft) | `ms-vscode.cmake-tools` | настройка, сборка и запуск проекта CMake |

Установить их можно на панели **Extensions** (`Ctrl+Shift+X`, в macOS `Cmd+Shift+X`): найдите по названию и нажмите **Install**. Или командой в терминале:
```sh
code --install-extension ms-vscode.cpptools
code --install-extension ms-vscode.cmake-tools
```
Когда вы откроете папку репозитория, VS Code сам предложит установить эти расширения — в репозитории они записаны как рекомендуемые.

Необязательное: **clangd** (`llvm-vs-code-extensions.vscode-clangd`) — подсказки и сообщения об ошибках на основе компилятора Clang, замечания clang-tidy появляются прямо во время набора. Если установите его, отключите подсказки расширения C/C++, чтобы они не дублировались: `Ctrl+Shift+P` → *Preferences: Open User Settings (JSON)* → добавьте строку `"C_Cpp.intelliSenseEngine": "disabled"`.

Остальное уже настроено в папке `.vscode/` репозитория: CMake Tools работает с пресетами из `CMakePresets.json`, код форматируется по стилю курса при сохранении, clang-tidy проверяет открытый файл, **F5** запускает отладку. Как открыть проект, собрать и запустить программу — в разделе «Сборка и запуск» файла [README.md](README.md).

## 4. Git и GitHub

1. Зарегистрируйтесь на https://github.com (если аккаунта ещё нет). Логин сообщите преподавателю лабораторных.
2. Представьтесь Git и задайте способ получения изменений:
   ```sh
   git config --global user.name "Иван Петров"              # имя — в каждом вашем коммите
   git config --global user.email "ivan.petrov@example.com"  # почта, привязанная к аккаунту GitHub
   git config --global pull.rebase false                     # git pull объединяет изменения слиянием
   git config --global core.editor "code --wait"             # сообщения коммитов Git просит ввести в VS Code
   ```
   По почте GitHub связывает коммиты с вашим аккаунтом. Если не хотите показывать свою почту, укажите адрес вида `…@users.noreply.github.com` из **Settings → Emails** на GitHub. Третья и четвёртая строки нужны для получения новых лабораторных ([WORKFLOW.md](WORKFLOW.md), раздел 1) после того, как вы сдали первую.

   **Зачем `pull.rebase false`.** Когда сданная работа слита (**Merge pull request**, [WORKFLOW.md](WORKFLOW.md), раздел 4), ветка `main` вашего репозитория и ветка `main` репозитория преподавателя **расходятся**:
   ```text
   main преподавателя:  A ── B         B — новая лабораторная
                         \
   ваш main:              └── M         M — слияние вашей ветки lab-01
   ```
   У вас есть коммит `M`, которого нет у преподавателя, у преподавателя — коммит `B`, которого нет у вас. Получая `B` (`git pull upstream main`), Git должен объединить разошедшиеся истории — **слиянием** (создать новый коммит с двумя родителями, `M` и `B`; история не меняется) или **перебазированием** (переписать ваши коммиты поверх `B`; история меняется, и следующая отправка в ваш репозиторий будет отклонена). Сам Git этот выбор не делает и останавливается с ошибкой `fatal: Need to specify how to reconcile divergent branches`. Настройка `pull.rebase false` задаёт способ: объединять слиянием. Без неё вторую и следующие лабораторные получить не удастся — ни командой, ни в VS Code (**Git: Pull from…** выполняет ту же команду `git pull`).

   **Зачем `core.editor "code --wait"`.** Слияние — тоже коммит, и у него должно быть сообщение. Git предлагает стандартное («Merge branch 'main' of …») и открывает редактор, чтобы его можно было исправить; пока редактор не закрыт, команда не завершится. Если редактор не настроен, Git открывает консольный редактор прямо в терминале — обычно **vim** (выход с сохранением: набрать `:wq` и нажать Enter), в Ubuntu и Debian — **nano** (выход: `Ctrl+X`, затем `Y` и Enter); кто этого не знает, видит непонятный экран, и кажется, что терминал завис. Настройка открывает вместо консольного редактора вкладку VS Code: `code` — открыть в VS Code, `--wait` — ждать, пока вкладку закроют. Проверьте или исправьте сообщение, сохраните (`Ctrl+S`, в macOS `Cmd+S`) и закройте вкладку — Git продолжит работу. Та же вкладка откроется, если выполнить `git commit` без `-m`.

   В командах получения новой лабораторной ([WORKFLOW.md](WORKFLOW.md), раздел 1) стоит ещё и ключ `--no-edit` (`git pull --no-edit upstream main`): он принимает стандартное сообщение слияния, и редактор вообще не открывается. Настройка `core.editor` нужна на случай, когда Git всё же попросит ввести сообщение.
3. Войдите в GitHub — без этого Git не сможет отправлять изменения, а пароль от GitHub для этого не подходит. Способов два, оба через браузер:
   - **VS Code:** при первой отправке (**Sync Changes** на панели **Source Control** или `git push` во встроенном терминале VS Code, например в разделе 5) VS Code предложит войти в GitHub — нажмите **Allow** и подтвердите вход в браузере. Вход действует для Git в VS Code, в том числе во встроенном терминале.
   - **Командная строка:** выполните
     ```sh
     gh auth login
     ```
     и ответьте на вопросы: **GitHub.com** → **HTTPS** → **Yes** (использовать вход для Git) → **Login with a web browser**; в браузере введите показанный код. После этого Git отправляет изменения без пароля из любого терминала.

   Достаточно одного способа. Если вы отправляете изменения не только из VS Code, но и из отдельного терминала, выполните `gh auth login`. Если позже VS Code всё равно предложит войти в GitHub, согласитесь.

## 5. Своя копия репозитория (один раз)

Решения лабораторных не должны быть видны другим студентам, поэтому работа ведётся не в форке (форк публичного репозитория на GitHub тоже публичный), а в **собственном приватном репозитории** — копии репозитория преподавателя. Репозиторий преподавателя подключается к копии под именем `upstream`: из него приходят новые лабораторные. Ваш репозиторий на GitHub называется `origin`: туда вы отправляете свою работу.

1. На GitHub нажмите **+** → **New repository**: имя `cpp-labs`, видимость **Private**, **без** README, `.gitignore` и лицензии (иначе первая отправка будет отклонена) → **Create repository**.
2. Откройте терминал. Проще всего встроенный в VS Code: меню **Terminal → New Terminal** (в Windows и Linux меню — вверху окна VS Code, в macOS — в строке меню вверху экрана) или сочетание клавиш `` Ctrl+` `` — клавиша слева от `1`, на русской раскладке `Ё` (в macOS тоже `Ctrl`). Терминал появится в нижней части окна; по умолчанию в Windows это PowerShell, в macOS — zsh, в Linux — обычно bash. Он открывается в папке, открытой в VS Code, а если папка не открыта — в вашей домашней папке.

   Перейдите в папку, где будут лежать ваши проекты, например `cd Documents` (её содержимое покажет команда `ls`), и выполните (один раз; эти команды проще набрать, чем повторить через меню):
   ```sh
   git clone https://github.com/learn-cpp-coding-from-scratch/cpp-labs.git
   cd cpp-labs
   git remote rename origin upstream                                # репозиторий преподавателя — upstream
   git remote add origin https://github.com/<ваш-логин>/cpp-labs.git # ваш репозиторий — origin
   git push -u origin main
   ```
3. Пригласите преподавателя: на странице своего репозитория **Settings → Collaborators → Add people** → логин преподавателя лабораторных (логин сообщит преподаватель). Преподаватель должен принять приглашение; до этого он не видит ваш репозиторий и его нельзя выбрать рецензентом.
4. Проверьте: команда `git remote -v` должна показать `origin` — ваш репозиторий и `upstream` — репозиторий преподавателя.

Откройте папку `cpp-labs` в VS Code (**File → Open Folder**) — именно корневую папку репозитория, а не папку отдельной лабораторной. На вопрос *Do you trust the authors of the files in this folder?* ответьте **Yes, I trust the authors**: иначе VS Code откроет папку в ограниченном режиме, и сборка не заработает (подробнее — в [README.md](README.md)). Дальше с Git можно работать в VS Code или в командной строке — для каждого шага в [WORKFLOW.md](WORKFLOW.md) даны оба способа. Настройка закончена: переходите к [WORKFLOW.md](WORKFLOW.md).
