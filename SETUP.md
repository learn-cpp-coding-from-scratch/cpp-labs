# Настройка окружения и сдача лабораторных

Краткая шпаргалка по командам Git и сообщениям коммитов — в [GIT.md](GIT.md).
- Разделы 1–5 выполняются один раз, в начале семестра: установить инструменты (раздел 1), проверить установку (2), настроить VS Code (3) и Git (4), сделать свою копию репозитория (5).
- Разделы 6–8 повторяются для каждой лабораторной: как получить её, выполнить и сдать. Основные способы работы с Git в курсе — **Git, встроенный в VS Code** (панель **Source Control**), и **командная строка**; для каждого шага даны оба, пользуйтесь любым. ## 1. Установка инструментов

Для лабораторных нужны:

| Программа | Зачем |
|---|---|
| компилятор C++ (g++ или clang++) и отладчик (gdb или lldb) | компиляция и отладка программ |
| CMake и Ninja | сборка проекта |
| clang-tidy и clang-format | проверка и форматирование кода по стилю курса |
| Git и GitHub CLI (`gh`) | работа с репозиторием и вход в GitHub |
| VS Code | среда разработки |

Устанавливайте программы менеджером пакетов, как ниже: так нужные версии ставятся и обновляются командами, без поиска установщиков на разных сайтах.

**Как связаны CMake и Ninja.** Сборка идёт в два этапа. **CMake** читает описание проекта (`CMakeLists.txt`: какие программы, из каких файлов, с какими флагами), находит компилятор и инструменты, находит или скачивает библиотеку тестирования Google Test и пишет подробный план сборки — файл `build.ninja` в папке сборки (для пресета `debug` — `build/debug/build.ninja`). Сам CMake ничего не компилирует. **Ninja** выполняет этот план: запускает компилятор, clang-tidy и компоновщик в нужном порядке, по несколько команд одновременно (по умолчанию — по числу ядер процессора с небольшим запасом) и повторяет только те шаги, результат которых зависит от файлов, изменившихся с прошлой сборки (если не изменилось ничего, он пишет `ninja: no work to do.`). Вручную запускать Ninja не нужно — это делают CMake и VS Code (кнопка **Build**), но установлен он должен быть: настройки проекта (`CMakePresets.json`) указывают именно его.

### Windows

**Что такое MSYS2, MinGW-w64 и UCRT64.** В Windows курс использует компилятор **g++** из коллекции компиляторов **GCC** проекта GNU — тот же, что в Linux, — и отладчик **gdb** того же проекта. Чтобы GCC создавал программы для Windows, ему нужны заголовочные файлы и библиотеки для вызова функций Windows (Windows API) и стандартной библиотеки языка C из состава Windows. Их предоставляет проект **MinGW-w64** (Minimalist GNU for Windows); GCC вместе с ними создаёт обычные программы Windows (`.exe`). GCC и gdb, собранные для Windows с MinGW-w64, называют набором инструментов (toolchain) MinGW-w64. Готовые сборки GCC, gdb и остальных инструментов курса для Windows устанавливаются через **MSYS2** — набор программ для Windows с терминалом bash и менеджером пакетов `pacman`, который устанавливает и обновляет пакеты одной командой (как `apt` в Linux или `brew` в macOS). В MSYS2 есть несколько **окружений** — независимых наборов пакетов, у каждого свой терминал и своя папка. Курс использует окружение **UCRT64**: его программы используют **UCRT** (Universal C Runtime) — библиотеку среды выполнения языка C, встроенную в Windows 10 и 11; это окружение MSYS2 рекомендует по умолчанию. Поэтому пакеты устанавливаются в терминале **MSYS2 UCRT64**, их имена начинаются с `mingw-w64-ucrt-x86_64-`, а программы оказываются в папке `C:\msys64\ucrt64\bin` (если MSYS2 установлена в папку по умолчанию).

1. Установите среду **MSYS2** со страницы https://www.msys2.org (установщик, путь по умолчанию `C:\msys64`).
2. Откройте из меню «Пуск» терминал **MSYS2 UCRT64** и выполните (на вопросы отвечайте Enter, после первой команды терминал может закрыться — откройте его снова и повторите её):
   ```sh
   pacman -Syu
   pacman -S mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-gdb \
             mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja \
             mingw-w64-ucrt-x86_64-clang mingw-w64-ucrt-x86_64-clang-tools-extra
   ```

   | Пакет `mingw-w64-ucrt-x86_64-…` | Что внутри |
   |---|---|
   | `gcc` | компиляторы GCC: `gcc` (язык C) и `g++` (язык C++) |
   | `gdb` | отладчик gdb — им VS Code отлаживает программы по F5 |
   | `cmake`, `ninja` | CMake и Ninja — сборка проекта |
   | `clang`, `clang-tools-extra` | инструменты проекта LLVM: clang-format (форматирование кода) и clang-tidy (проверка стиля и типичных ошибок при каждой сборке); компилятор Clang из этих пакетов курс не использует |
3. Добавьте папку `C:\msys64\ucrt64\bin` в переменную среды `Path`: **Параметры → Система → О системе → Дополнительные параметры системы → Переменные среды**, в разделе «Переменные среды пользователя» выберите `Path` → **Изменить** → **Создать**. Команды вроде `g++`, `cmake`, `ninja` Windows ищет в папках из `Path`, поэтому без этого VS Code и обычный терминал Windows их не найдут. Добавлять нужно именно `ucrt64\bin`. Папки `mingw64\bin`, `clang64\bin` и `usr\bin` принадлежат другим окружениям MSYS2: их программы собраны для других библиотек среды выполнения, и если такая папка окажется в `Path` раньше `ucrt64\bin`, будут запускаться не те программы.
4. В **PowerShell** установите Git, GitHub CLI и VS Code:
   ```powershell
   winget install Git.Git GitHub.cli Microsoft.VisualStudioCode
   ```
5. Перезагрузите компьютер (или хотя бы закройте все терминалы), чтобы изменения `Path` вступили в силу.

**Другой вариант компилятора для Windows — MSVC.** Вместо MSYS2 (пункты 1–3) можно взять компилятор Microsoft **MSVC**. Он устанавливается вместе со средой разработки **Visual Studio** (это отдельная программа, не VS Code): в установщике Visual Studio выберите компонент «Разработка классических приложений на C++» — с ним устанавливаются компилятор MSVC, CMake, Ninja и clang-format. clang-tidy устанавливается дополнительно: компонент «Инструменты C++ Clang для Windows» в том же установщике или командой `winget install LLVM.LLVM`. Visual Studio в этом варианте нужна только как источник компилятора и инструментов: лабораторные вы по-прежнему выполняете в **VS Code**, как описано ниже, и выбираете в нём пресет **Debug (MSVC)** вместо **Debug (GCC/Clang)**. Git, GitHub CLI и VS Code установите командой из пункта 4.

### macOS

Откройте приложение **Терминал** и выполните по очереди. Команда `xcode-select --install` открывает отдельное окно установки: нажмите **Install** и дождитесь окончания (несколько минут), только потом выполняйте следующие команды. Сообщение `command line tools are already installed` не ошибка: инструменты уже есть, переходите дальше.
```sh
setopt interactivecomments
echo 'setopt interactivecomments' >> ~/.zshrc
xcode-select --install          # компилятор clang++, отладчик lldb, git

# менеджер пакетов Homebrew (команда со страницы https://brew.sh); в конце установщик
# выведет в разделе Next steps команды для добавления Homebrew в PATH — выполните их
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

brew install cmake ninja clang-format llvm gh
brew install --cask visual-studio-code

# clang-tidy входит в пакет llvm, но Homebrew не делает его доступной командой — создаём ссылку
ln -s "$(brew --prefix llvm)/bin/clang-tidy" "$(brew --prefix)/bin/clang-tidy"
# clang-tidy из Homebrew не знает, где лежат стандартные заголовки macOS — подсказываем ему
echo 'export SDKROOT="$(xcrun --show-sdk-path)"' >> ~/.zprofile
```
После этого закройте и снова откройте терминал и VS Code.

Если VS Code установлен не через Homebrew, а скачан с сайта https://code.visualstudio.com, команда `code` в терминале сама не появляется. Подключите её: откройте VS Code → `Cmd+Shift+P` → **Shell Command: Install 'code' command in PATH** → Enter, затем откройте новое окно терминала. Команда `code` нужна для установки расширений из терминала (раздел 3) и для настройки Git (раздел 4).

Первые две строки нужны из-за оболочки zsh, которая по умолчанию работает в терминале macOS: в ней текст после `#` в командах, набранных или вставленных в терминал, по умолчанию **не** считается комментарием, а передаётся команде как аргументы — и команда вида `git push   # пояснение` завершится ошибкой. Команда `setopt interactivecomments` включает комментарии в текущем окне терминала, а строка в файле `~/.zshrc` — во всех следующих. В этой инструкции пояснения после `#` стоят во многих командах, поэтому выполните эти строки первыми. В Windows (PowerShell) и Linux (bash) комментарии работают без настройки.

### Linux (Debian, Ubuntu)

```sh
sudo apt update
sudo apt install build-essential gdb cmake ninja-build git gh clang-format clang-tidy
sudo snap install code --classic        # VS Code
```
Проекту нужен CMake 3.24 или новее (проверка — в разделе 2). В Ubuntu 24.04 и Debian 12 `apt` ставит подходящую версию, а в Ubuntu 22.04 — 3.22; в этом случае установите CMake из snap: `sudo snap install cmake --classic`.

Если `snap` нет, скачайте пакет VS Code `.deb` со страницы https://code.visualstudio.com и установите его: `sudo apt install ./code_*.deb`. В других дистрибутивах те же программы устанавливаются их менеджером пакетов (в Fedora — `sudo dnf install gcc-c++ gdb cmake ninja-build git gh clang-tools-extra`).

## 2. Проверка установки

Откройте **новый** терминал (в Windows — PowerShell или терминал VS Code) и выполните:
```sh
g++ --version
cmake --version
ninja --version
clang-tidy --version
clang-format --version
git --version
gh --version
code --version
```
Блок можно скопировать и вставить в терминал целиком (`Ctrl+V`, в macOS `Cmd+V`), затем нажать Enter: команды выполнятся по очереди. Каждая команда должна вывести номер версии; версия CMake должна быть 3.24 или новее. В macOS команда `g++` запускает компилятор clang++ — так и должно быть. Сообщение `command not found` (в PowerShell — «Имя … не распознано как имя командлета, функции, файла сценария или выполняемой программы», в командной строке Windows — «… не является внутренней или внешней командой») означает, что программа не установлена или её папки нет в `PATH`; после изменения `PATH` перезапустите терминал и VS Code.

## 3. VS Code: расширения и настройка

Обязательные расширения:

| Расширение | Идентификатор | Зачем |
|---|---|---|
| **C/C++** (Microsoft) | `ms-vscode.cpptools` | подсветка и подсказки (IntelliSense), отладка, проверка clang-tidy, форматирование |
| **CMake Tools** (Microsoft) | `ms-vscode.cmake-tools` | настройка, сборка и запуск проекта CMake |

Установить их можно на панели **Extensions** (`Ctrl+Shift+X`, в macOS `Cmd+Shift+X`): найдите по названию и нажмите **Install**. Или командой в терминале:
```sh
code --install-extension ms-vscode.cpptools
code --install-extension ms-vscode.cmake-tools
```
Когда вы откроете папку репозитория, VS Code сам предложит установить эти расширения — в репозитории они записаны как рекомендуемые.

Необязательное: **clangd** (`llvm-vs-code-extensions.vscode-clangd`) — подсказки и сообщения об ошибках на основе компилятора Clang, замечания clang-tidy появляются прямо во время набора. Если установите его, отключите подсказки расширения C/C++, чтобы они не дублировались: `Ctrl+Shift+P` → *Preferences: Open User Settings (JSON)* → добавьте строку `"C_Cpp.intelliSenseEngine": "disabled"`.

Остальное уже настроено в папке `.vscode/` репозитория: CMake Tools работает с пресетами из `CMakePresets.json`, код форматируется по стилю курса при сохранении, clang-tidy проверяет открытый файл, **F5** запускает отладку. Как открыть проект, собрать и запустить программу — в разделе «Сборка и запуск» файла [README.md](README.md).

## 4. Git и GitHub

1. Зарегистрируйтесь на https://github.com (если аккаунта ещё нет). Логин сообщите преподавателю лабораторных.
2. Представьтесь Git и задайте способ получения изменений:
   ```sh
   git config --global user.name "Иван Петров"              # имя — в каждом вашем коммите
   git config --global user.email "ivan.petrov@example.com"  # почта, привязанная к аккаунту GitHub
   git config --global pull.rebase false                     # git pull объединяет изменения слиянием
   git config --global core.editor "code --wait"             # сообщения коммитов Git просит ввести в VS Code
   ```
   По почте GitHub связывает коммиты с вашим аккаунтом. Если не хотите показывать свою почту, укажите адрес вида `…@users.noreply.github.com` из **Settings → Emails** на GitHub. Третья и четвёртая строки нужны для получения новых лабораторных (раздел 6) после того, как вы сдали первую.

   **Зачем `pull.rebase false`.** Когда сданная работа слита (**Merge pull request**, раздел 8), ветка `main` вашего репозитория и ветка `main` репозитория преподавателя **расходятся**:
   ```text
   main преподавателя:  A ── B         B — новая лабораторная
                         \
   ваш main:              └── M         M — слияние вашей ветки lab-01
   ```
   У вас есть коммит `M`, которого нет у преподавателя, у преподавателя — коммит `B`, которого нет у вас. Получая `B` (`git pull upstream main`), Git должен объединить разошедшиеся истории — **слиянием** (создать новый коммит с двумя родителями, `M` и `B`; история не меняется) или **перебазированием** (переписать ваши коммиты поверх `B`; история меняется, и следующая отправка в ваш репозиторий будет отклонена). Сам Git этот выбор не делает и останавливается с ошибкой `fatal: Need to specify how to reconcile divergent branches`. Настройка `pull.rebase false` задаёт способ: объединять слиянием. Без неё вторую и следующие лабораторные получить не удастся — ни командой, ни в VS Code (**Git: Pull from…** выполняет ту же команду `git pull`).

   **Зачем `core.editor "code --wait"`.** Слияние — тоже коммит, и у него должно быть сообщение. Git предлагает стандартное («Merge branch 'main' of …») и открывает редактор, чтобы его можно было исправить; пока редактор не закрыт, команда не завершится. Если редактор не настроен, Git открывает консольный редактор прямо в терминале — обычно **vim** (выход с сохранением: набрать `:wq` и нажать Enter), в Ubuntu и Debian — **nano** (выход: `Ctrl+X`, затем `Y` и Enter); кто этого не знает, видит непонятный экран, и кажется, что терминал завис. Настройка открывает вместо консольного редактора вкладку VS Code: `code` — открыть в VS Code, `--wait` — ждать, пока вкладку закроют. Проверьте или исправьте сообщение, сохраните (`Ctrl+S`, в macOS `Cmd+S`) и закройте вкладку — Git продолжит работу. Та же вкладка откроется, если выполнить `git commit` без `-m`.

   В командах раздела 6 стоит ещё и ключ `--no-edit` (`git pull --no-edit upstream main`): он принимает стандартное сообщение слияния, и редактор вообще не открывается. Настройка `core.editor` нужна на случай, когда Git всё же попросит ввести сообщение.
3. Войдите в GitHub — без этого Git не сможет отправлять изменения, а пароль от GitHub для этого не подходит. Способов два, оба через браузер:
   - **VS Code:** при первой отправке (**Sync Changes** на панели **Source Control** или `git push` во встроенном терминале VS Code, например в разделе 5) VS Code предложит войти в GitHub — нажмите **Allow** и подтвердите вход в браузере. Вход действует для Git в VS Code, в том числе во встроенном терминале.
   - **Командная строка:** выполните
     ```sh
     gh auth login
     ```
     и ответьте на вопросы: **GitHub.com** → **HTTPS** → **Yes** (использовать вход для Git) → **Login with a web browser**; в браузере введите показанный код. После этого Git отправляет изменения без пароля из любого терминала.

   Достаточно одного способа. Если вы отправляете изменения не только из VS Code, но и из отдельного терминала, выполните `gh auth login`. Если позже VS Code всё равно предложит войти в GitHub, согласитесь.

## 5. Своя копия репозитория (один раз)

Решения лабораторных не должны быть видны другим студентам, поэтому работа ведётся не в форке (форк публичного репозитория на GitHub тоже публичный), а в **собственном приватном репозитории** — копии репозитория преподавателя. Репозиторий преподавателя подключается к копии под именем `upstream`: из него приходят новые лабораторные. Ваш репозиторий на GitHub называется `origin`: туда вы отправляете свою работу.

1. На GitHub нажмите **+** → **New repository**: имя `cpp-labs`, видимость **Private**, **без** README, `.gitignore` и лицензии (иначе первая отправка будет отклонена) → **Create repository**.
2. Откройте терминал. Проще всего встроенный в VS Code: меню **Terminal → New Terminal** (в Windows и Linux меню — вверху окна VS Code, в macOS — в строке меню вверху экрана) или сочетание клавиш `` Ctrl+` `` — клавиша слева от `1`, на русской раскладке `Ё` (в macOS тоже `Ctrl`). Терминал появится в нижней части окна; по умолчанию в Windows это PowerShell, в macOS — zsh, в Linux — обычно bash. Он открывается в папке, открытой в VS Code, а если папка не открыта — в вашей домашней папке.

   Перейдите в папку, где будут лежать ваши проекты, например `cd Documents` (её содержимое покажет команда `ls`), и выполните (один раз; эти команды проще набрать, чем повторить через меню):
   ```sh
   git clone https://github.com/learn-cpp-coding-from-scratch/cpp-labs.git
   cd cpp-labs
   git remote rename origin upstream                                # репозиторий преподавателя — upstream
   git remote add origin https://github.com/<ваш-логин>/cpp-labs.git # ваш репозиторий — origin
   git push -u origin main
   ```
3. Пригласите преподавателя: на странице своего репозитория **Settings → Collaborators → Add people** → логин преподавателя лабораторных (логин сообщит преподаватель). Преподаватель должен принять приглашение; до этого он не видит ваш репозиторий и его нельзя выбрать рецензентом.
4. Проверьте: команда `git remote -v` должна показать `origin` — ваш репозиторий и `upstream` — репозиторий преподавателя.

Откройте папку `cpp-labs` в VS Code (**File → Open Folder**) — именно корневую папку репозитория, а не папку отдельной лабораторной. На вопрос *Do you trust the authors of the files in this folder?* ответьте **Yes, I trust the authors**: иначе VS Code откроет папку в ограниченном режиме, и сборка не заработает (подробнее — в [README.md](README.md)). Дальше с Git можно работать в VS Code или в командной строке — для каждого шага ниже даны оба способа.

**Где в VS Code Git.** Панель **Source Control** (значок с ветвями на левой боковой панели или `Ctrl+Shift+G`, в macOS `Cmd+Shift+G`) — изменённые файлы, коммиты, отправка. Имя текущей ветки — в строке состояния внизу слева; щелчок по нему открывает список веток. Команды Git есть и в палитре команд: `Ctrl+Shift+P` (`Cmd+Shift+P`) → наберите `Git:`.

## 6. Получить новую лабораторную

Делайте это, когда преподаватель выложил новую лабораторную.

**VS Code:**
1. Перейдите в ветку `main`: щёлкните по имени ветки в строке состояния → выберите `main`.
2. Получите изменения из своего репозитория на GitHub (например, слитые ранее лабораторные): на панели **Source Control** нажмите **Sync Changes** (или значок со стрелками в строке состояния).
3. `Ctrl+Shift+P` → **Git: Pull from…** → выберите удалённый репозиторий `upstream` → ветку `upstream/main`. Новые папки лабораторных появятся в проводнике.
4. Отправьте обновления в свой репозиторий: снова **Sync Changes**.

**Командная строка:**
```sh
git switch main
git pull                           # изменения из своего репозитория на GitHub
git pull --no-edit upstream main   # новые лабораторные из репозитория преподавателя; --no-edit — стандартное сообщение слияния
git push                           # отправить их в свой репозиторий
```

Новые лабораторные приходят новыми папками и не затрагивают уже сделанную работу. Изменяйте только файлы решения в папке `src/` задачи (состав файлов описан в её `README.md`), свои тесты в `tests/student/` и свои модули библиотеки в подпапках `common/…/student/` (см. [common/README.md](common/README.md)); объявления функций не меняйте. Остальные файлы преподавателя (`CMakeLists.txt`, `CMakePresets.json`, `cmake/`, `.clang-format`, `.clang-tidy`, `.vscode/`, `README.md`) не трогайте: если преподаватель тоже изменит такой файл, при получении обновлений возникнет конфликт, а проверка решения всё равно выполняется с исходными файлами.

## 7. Выполнить лабораторную

Каждая лабораторная выполняется в своей ветке `lab-NN`, где `NN` — номер лабораторной.

**VS Code:**
1. **Создать ветку.**
   - Проверьте, что вы в ветке `main`: в левом нижнем углу окна, в строке состояния, рядом со значком ветвления написано имя текущей ветки — должно быть `main`. Проверьте, что новая лабораторная получена (раздел 6): на панели **Explorer** (`Ctrl+Shift+E`, в macOS `Cmd+Shift+E`) есть её папка, например `lab-01_linear-algorithms`.
   - Щёлкните по имени ветки `main` в строке состояния. Вверху по центру окна откроется список: пункты **+ Create new branch…**, **+ Create new branch from…** и ниже — существующие ветки.
   - Выберите **+ Create new branch…**, введите `lab-01` и нажмите Enter.
   - В строке состояния вместо `main` появится `lab-01`: ветка создана от ветки `main`, в которой вы были, и VS Code уже переключился на неё.

   Если имени ветки в строке состояния не видно, создайте ветку через палитру команд: `Ctrl+Shift+P` (в macOS `Cmd+Shift+P`) → **Git: Create Branch…** → `lab-01` → Enter.
2. **Решайте задачи** (как устроена задача — в [README.md](README.md)).
3. **Сохраняйте работу коммитом** после каждой решённой задачи:
   - откройте панель **Source Control** — там список изменённых файлов; щелчок по файлу показывает, что в нём изменилось;
   - нажмите **+** у файлов, которые входят в коммит (или **+** у заголовка **Changes** — все сразу);
   - введите сообщение в поле **Message**, например `feat(lab-01): реализовать задачу 3 — обмен значений`, и нажмите **Commit**.
4. **Отправьте ветку на GitHub:** первый раз — кнопка **Publish Branch**, дальше — **Sync Changes**.

**Командная строка:**
```sh
git switch main
git switch -c lab-01                  # создать ветку и перейти в неё
git add lab-01_linear-algorithms
git commit -m "feat(lab-01): реализовать задачу 3 — обмен значений"
git push -u origin lab-01             # первая отправка ветки; дальше достаточно git push
```

Как часто коммитить, как писать сообщения коммитов и другие полезные команды Git — в шпаргалке [GIT.md](GIT.md).

## 8. Сдать лабораторную

Запрос на слияние создаётся, рецензируется и сливается **в браузере, на сайте GitHub** — при любом способе работы с Git (пункты 2, 3 и 5).

**VS Code и GitHub:**
1. Отправьте последние коммиты: **Sync Changes**.
2. Откройте в **браузере** страницу своего репозитория на сайте GitHub: `https://github.com/<ваш-логин>/cpp-labs` (войдите в аккаунт, если сайт попросит). Вверху страницы откройте вкладку **Pull requests** → кнопка **New pull request** → в списках выберите **base: `main`** и **compare: `lab-01`** → **Create pull request**. В описании перечислите решённые задачи. Если ветка отправлена недавно, на главной странице репозитория GitHub сам показывает строку «lab-01 had recent pushes…» с кнопкой **Compare & pull request** — она открывает ту же форму.
3. В той же форме в браузере, в правой колонке, в поле **Reviewers** выберите преподавателя лабораторных (если забыли, рецензента можно выбрать и позже — на странице уже созданного запроса на слияние, в той же правой колонке).
4. Преподаватель запускает на вашем решении свои тесты и оставляет замечания к строкам кода. Исправляйте их **в той же ветке**: проверьте в строке состояния, что вы в `lab-01`, внесите исправления, сделайте коммит (например, `fix(lab-01): исправить обработку отрицательных чисел в задаче 3`) и нажмите **Sync Changes** — исправления сразу появятся в том же запросе на слияние.
5. Когда преподаватель одобрит работу (**Approve**), на странице запроса на слияние в браузере нажмите **Merge pull request** → **Confirm merge**. Затем в VS Code перейдите в ветку `main` и нажмите **Sync Changes** — слитая работа появится и у вас.

**Командная строка** — отправка (пункт 1), исправления (пункт 4) и обновление `main` после слияния (пункт 5):
```sh
git push                              # пункт 1
git switch lab-01                     # пункт 4
git commit -am "fix(lab-01): исправить обработку отрицательных чисел в задаче 3"   # -a: все изменённые отслеживаемые файлы; новый файл сначала git add
git push
# после Merge pull request на GitHub:
git switch main
git pull
```

Срок сдачи каждой лабораторной указан в её `README.md`. Лабораторная считается сданной, когда запрос на слияние одобрен.

### После слияния: удалите ветку лабораторной

После **Merge pull request** ветка `lab-01` сама не удаляется: она остаётся и на GitHub, и на вашем компьютере. Удалите её в обоих местах:

1. **На GitHub (в браузере).** Сразу после слияния на странице запроса на слияние появляется кнопка **Delete branch** — нажмите её.
2. **На компьютере.** Перейдите в ветку `main` (её нужно обновить — **Sync Changes**, см. пункт 5) и удалите `lab-01`:
   - **VS Code:** `Ctrl+Shift+P` (в macOS `Cmd+Shift+P`) → **Git: Delete Branch…** → выберите `lab-01`;
   - **командная строка:** `git branch -d lab-01`.
3. **Уберите запись об удалённой ветке GitHub** (`origin/lab-01`, она остаётся у вас после шага 1): **VS Code** — `Ctrl+Shift+P` → **Git: Fetch (Prune)**; **командная строка** — `git fetch --prune`.

Удалять текущую ветку Git не разрешает, поэтому сначала перейдите в `main`. Если ветка ещё не слита в `main`, команда `git branch -d` откажется её удалять (`not fully merged`), а VS Code предложит удалить принудительно — **откажитесь**: значит, `main` у вас не обновлена (выполните **Sync Changes** в `main`) или запрос на слияние ещё не слит. Так случайно потерять работу нельзя.

**Удаление ветки ничего не уничтожает.** Все коммиты `lab-01` после слияния входят в историю `main`. Запрос на слияние — со всеми коммитами, замечаниями преподавателя и одобрением — остаётся на GitHub во вкладке **Pull requests → Closed**, и для этого ветка не нужна.

**Можно и не удалять.** Если хотите видеть, какие ветки были, оставьте их: работе это не мешает, просто к концу семестра в списке будут `lab-01` … `lab-10`. Чтобы GitHub удалял ветки сам после каждого слияния, включите в своём репозитории **Settings → General → Automatically delete head branches**.

**Не продолжайте работу в ветке, которая уже слита.** Запрос на слияние после **Merge** закрыт, и новые коммиты в `lab-01` в него не попадут: ни в `main`, ни к преподавателю они сами не придут — для этого понадобится новый запрос на слияние. Кроме того, старая ветка создана от прежнего состояния `main`: в ней нет новых лабораторных и того, что слито позже, поэтому при новом слиянии вероятны конфликты. Если после слияния понадобилось что-то исправить, создайте **новую ветку от актуальной `main`**, например `lab-01-fix` (раздел 7), и сдайте исправление новым запросом на слияние. Удалённая после слияния ветка не даст по ошибке продолжить работу в старой.

## 9. Если вам удобнее GitHub Desktop

[GitHub Desktop](https://desktop.github.com) — отдельная программа для работы с Git мышкой: видны изменённые файлы, история и ветки. Основные способы в курсе — VS Code и командная строка (разделы 6–8); GitHub Desktop — для тех, кому он привычнее. Она есть для Windows и macOS (официальной версии для Linux нет). Установка: в Windows — `winget install GitHub.GitHubDesktop`, в macOS — `brew install --cask github`.

Первичная настройка (разделы 4 и 5) всё равно выполняется **в терминале**: GitHub Desktop не умеет подключать репозиторий преподавателя как `upstream`. После неё:

1. **Вход в GitHub.** При первом запуске нажмите **Sign in to GitHub.com** и войдите через браузер; на шаге **Configure Git** проверьте имя и почту.
2. **Подключить свою копию.** **File → Add Local Repository** → выберите папку `cpp-labs`.
3. **Получить новую лабораторную.**
   - В списке **Current Branch** выберите `main`.
   - Загрузите изменения преподавателя: **Repository → Open in Terminal** (в Windows пункт называется по оболочке, выбранной в настройках, например **Open in Command Prompt**) и выполните `git fetch upstream`.
   - **Branch → Merge into current branch** → выберите `upstream/main` → **Merge**.
   - Нажмите **Push origin**, чтобы отправить обновления в свой репозиторий.
4. **Начать лабораторную.** **Branch → New branch** → имя `lab-01`, основа — `main` → **Create branch**.
5. **Сохранить работу.** Отметьте изменённые файлы слева, внизу введите сообщение (например, `feat(lab-01): реализовать задачу 3 — обмен значений`) → **Commit to lab-01**. Затем **Publish branch** (первый раз) или **Push origin**.
6. **Сдать.** **Branch → Create Pull Request** — откроется браузер; проверьте **base: `main`** и **compare: `lab-01`**, выберите преподавателя в **Reviewers** → **Create pull request**. Исправления по замечаниям — новые коммиты в той же ветке и **Push origin**.
7. **После одобрения** нажмите на GitHub **Merge pull request**, затем в GitHub Desktop выберите ветку `main` и нажмите **Fetch origin** → **Pull origin**.

GitHub Desktop и VS Code работают с одной и той же папкой: можно писать код в VS Code, а коммитить и отправлять в GitHub Desktop.

## 10. Если что-то не работает

| Сообщение или симптом | Что сделать |
|---|---|
| `CMake was unable to find a build program corresponding to "Ninja"` | Ninja не установлен или его папки нет в `PATH` (в Windows — `C:\msys64\ucrt64\bin`, см. раздел 1) |
| `No CMAKE_CXX_COMPILER could be found` | компилятор не установлен или его папки нет в `PATH`; перезапустите VS Code после изменения `PATH` |
| `clang-tidy не найден — сборка без проверки стиля` | установите clang-tidy (в macOS — команда `ln -s …` из раздела 1) |
| macOS: `'cctype' file not found` при проверке clang-tidy | не выполнена команда `echo 'export SDKROOT=…'` из раздела 1; выполните её и перезапустите терминал и VS Code |
| macOS: `zsh: command not found: code` | VS Code скачан с сайта: в VS Code `Cmd+Shift+P` → **Shell Command: Install 'code' command in PATH**, затем новое окно терминала |
| VS Code не предлагает пресеты, нет панели CMake | открыта не корневая папка репозитория или не установлено расширение CMake Tools |
| Ошибки `#include` в редакторе, хотя проект собирается | `Ctrl+Shift+P` → **CMake: Delete Cache and Reconfigure** |
| При первой настройке проекта — ошибка загрузки googletest | CMake скачивает библиотеку тестирования из интернета; проверьте подключение и повторите |
| `git push` → `Authentication failed`, `Permission … denied` или запрос пароля | войдите в GitHub одним из способов раздела 4, в отдельном терминале — командой `gh auth login`; проверьте командой `git remote -v`, что `origin` указывает на **ваш** репозиторий, а не на репозиторий преподавателя |
| `git pull` → `Need to specify how to reconcile divergent branches` | выполните `git config --global pull.rebase false` (раздел 4) и повторите |
| `git push` → `rejected … fetch first` | в репозитории на GitHub есть изменения, которых нет у вас: `git pull`, затем снова `git push` |
| `git pull upstream main` → `CONFLICT` | вы изменили файл преподавателя. Отмените слияние `git merge --abort`, верните файл командой `git checkout upstream/main -- <файл>`, сделайте коммит и повторите `git pull --no-edit upstream main`; если не получается — напишите преподавателю |
| Сделали коммит не в той ветке (например, в `main`) | ничего не удаляйте и напишите преподавателю — см. раздел «Отменить» в [GIT.md](GIT.md#отменить) |

Как вернуть испорченный файл, убрать лишний файл из коммита, исправить сообщение последнего коммита или отменить уже отправленный коммит — в разделе «Отменить» шпаргалки [GIT.md](GIT.md#отменить). Там же — какие команды выполнять нельзя.
