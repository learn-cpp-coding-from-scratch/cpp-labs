# Шпаргалка по Git

Команды для работы с лабораторными. Как настроить Git и сделать свою копию репозитория — в [SETUP.md](SETUP.md), разделы 4–5. В примерах `lab-01` — ветка первой лабораторной.

## Основной цикл: изменить → сохранить → отправить

```sh
git status                          # что изменилось и в какой ветке вы сейчас
git add lab-01_linear-algorithms    # добавить изменения папки в следующий коммит
git commit -m "feat(lab-01): реализовать задачу 3 — обмен значений"
git push                            # отправить коммиты в свой репозиторий на GitHub
```

Коммит сохраняет **только то, что добавлено командой `git add`** (в VS Code — кнопкой **+** на панели **Source Control**). Файлы, которые вы изменили, но не добавили, в коммит не попадут.

## Посмотреть

| Команда | Что показывает |
|---|---|
| `git status` | текущую ветку, изменённые файлы, что уже добавлено в коммит |
| `git diff` | изменения, ещё не добавленные в коммит, построчно |
| `git diff --staged` | изменения, уже добавленные командой `git add`, но ещё не вошедшие в коммит |
| `git log --oneline --graph --all` | историю коммитов всех веток, по одной строке на коммит |
| `git show` | последний коммит: сообщение и изменения |
| `git remote -v` | адреса удалённых репозиториев: `origin` — ваш, `upstream` — преподавателя |

Выход из длинного вывода (`git log`, `git diff`) — клавиша `q`.

## Ветки

| Команда | Что делает |
|---|---|
| `git branch` | список веток; текущая отмечена `*` |
| `git switch main` | перейти в ветку `main` |
| `git switch -c lab-02` | создать ветку `lab-02` от текущей и перейти в неё |
| `git branch -d lab-01` | удалить ветку `lab-01`, если она уже слита в текущую |
| `git fetch --prune` | убрать записи о ветках, удалённых на GitHub (например, `origin/lab-01` после **Delete branch**) |

После слияния ветку лабораторной удаляйте и не продолжайте в ней работу — исправления делайте в новой ветке от `main` (подробно — [WORKFLOW.md](WORKFLOW.md), раздел 4).

Перед переходом в другую ветку сделайте коммит. Иначе Git перенесёт незакоммиченные изменения в другую ветку или откажется переключаться с сообщением `Your local changes … would be overwritten`.

## Обмен с GitHub

| Команда | Что делает |
|---|---|
| `git push` | отправить коммиты текущей ветки в свой репозиторий |
| `git push -u origin lab-02` | отправить новую ветку первый раз; дальше достаточно `git push` |
| `git pull` | получить изменения текущей ветки из своего репозитория |
| `git pull --no-edit upstream main` | получить новые лабораторные из репозитория преподавателя (находясь в `main`) |
| `git merge --no-edit main` | перенести обновления из `main` в ветку лабораторной (находясь в `lab-NN`; только по просьбе преподавателя, см. [WORKFLOW.md](WORKFLOW.md#2-если-преподаватель-обновил-курс-пока-вы-работаете-в-ветке-lab-nn)) |

Порядок получения новой лабораторной и сдачи работы — в [WORKFLOW.md](WORKFLOW.md), разделы 1, 3 и 4.

## Отменить

| Ситуация | Команда |
|---|---|
| испортили файл и хотите вернуть его к последнему коммиту | `git restore <файл>` — **несохранённые изменения файла пропадут** |
| добавили в коммит лишний файл (`git add`), но ещё не сделали коммит | `git restore --staged <файл>` — файл останется изменённым, но не попадёт в коммит |
| опечатка в сообщении последнего коммита, коммит ещё **не отправлен** | `git commit --amend -m "Новое сообщение"` |
| нужно отменить уже отправленный коммит | `git revert <хеш>` — создаёт новый коммит, отменяющий изменения; хеш — код из 7 символов в начале строки `git log --oneline`, например `a1b2c3d` |
| сделали коммит не в той ветке (например, в `main`) | ничего не удаляйте и напишите преподавателю |

**Не выполняйте** `git push --force`, `git reset --hard` и `git rebase` для коммитов, уже отправленных на GitHub: они переписывают историю, и часть работы может пропасть. Ошибки вроде коммита не в той ветке исправимы, пока история не переписана, — поэтому, если что-то пошло не так, напишите преподавателю, ничего не удаляя.

## Как писать сообщение коммита

История полезна, только если по ней можно понять, что происходило в проекте. Хорошее сообщение коммита:

1. **Первая строка — короткое описание изменения** (до 50–70 символов) **в повелительном наклонении**: «Реализовать…», «Исправить…», «Добавить…», «Вынести…». Без точки в конце.
2. **Один коммит — одно логическое изменение.** Если в сообщении хочется написать «и», изменение лучше разделить на два коммита: добавьте в первый только относящиеся к нему файлы, сделайте коммит, затем второй.
3. **При необходимости — пояснение, зачем сделано изменение**: после первой строки пустая строка, затем текст. Что изменено, видно из самих изменений; в пояснении пишут причину.
4. **Один язык в проекте.** Пишите все сообщения по-русски (по-английски) и не смешивайте языки. Исключение — английские слова-типы Conventional Commits (см. ниже).

| Плохо | Почему | Хорошо |
|---|---|---|
| `fix` | не сказано, что исправлено | `Исправить целочисленное деление в задаче 4` |
| `изменения` | ничего не сообщает | `Вынести перевод единиц длины в функцию toMeters` |
| `lab 1 готово!!!` | не видно, что сделано | `Реализовать задачу 2 лабораторной 1: арифметические операции` |
| `Задача 3 и проверки для задачи 5` | два изменения в одном коммите | два коммита: `Реализовать задачу 3…` и `Добавить проверки в задачу 5` |
| `Исправил ошибку.` | не повелительное наклонение, точка в конце, не сказано какую | `Исправить знак остатка для отрицательных чисел` |

### Оформление по Conventional Commits (желательно)

В лабораторных и индивидуальном проекте сообщения желательно оформлять по распространённому соглашению **Conventional Commits**: по первому слову сразу видно, что за изменение, а историю могут читать и программы (например, собирать по ней список изменений новой версии).

```text
<тип>(<область>): <описание>
```

- **тип** — вид изменения, по-английски (таблица ниже); после него двоеточие и пробел;
- **область** — необязательная часть в скобках: к чему относится изменение; в лабораторных — номер лабораторной: `lab-01`;
- **описание** — по правилам выше: по-русски, в повелительном наклонении, без точки в конце, но **с маленькой буквы**: после двоеточия предложение продолжается.

| Тип | Когда | Пример |
|---|---|---|
| `feat` | новая функциональность: решена задача или её часть | `feat(lab-01): реализовать задачу 3 — обмен значений` |
| `fix` | исправление ошибки | `fix(lab-01): исправить обработку отрицательных чисел в задаче 3` |
| `test` | добавлены или изменены проверки (`assert`, тесты) | `test(lab-02): добавить проверки границ месяцев в задаче 5` |
| `refactor` | изменена структура кода без изменения поведения | `refactor(lab-02): вынести проверку високосного года в функцию` |
| `style` | только оформление: отступы, пробелы, переносы | `style(lab-01): привести код к clang-format` |
| `docs` | только комментарии и документация | `docs(lab-02): описать предусловия функций задачи 4` |
| `chore` | служебные изменения, не затрагивающие код программы | `chore: добавить build/ в .gitignore` |

Тип определяется тем, **зачем** сделано изменение. Если для коммита подходят сразу два типа (например, `fix` и `feat`), значит, в нём смешаны два изменения — разделите его на два коммита.

**Сообщение с пояснением.** В VS Code введите его в поле **Message** панели **Source Control**: первая строка, пустая строка, пояснение. В терминале выполните `git commit` без `-m`: откроется вкладка VS Code (если Git настроен по разделу 4 [SETUP.md](SETUP.md)). Введите текст, сохраните и закройте вкладку.

```text
fix(lab-02): исправить переполнение в задаче 1 семинара

Куб числа 1500 не помещается в int, поэтому вычисления
выполняются в long long.
```

**Как часто коммитить.** После каждой решённой задачи или её заметной части, и всегда — перед переходом в другую ветку: так видно ход работы, а к любому сохранённому состоянию можно вернуться. Перед коммитом проверьте, что проект собирается без ошибок и замечаний clang-tidy (в VS Code — панель **Problems**).
